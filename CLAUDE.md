# Claude Code Instructions

## Skills and Agents

At the start of each session, run `git pull` in `/usr/local/webpros-claude-skills/` to
ensure you have the latest skills and agents. That directory contains project-wide
skills (under `skills/`) and agents (under `agents/`) that provide commit message
standards, workflow conventions, and other shared guidance used across WebPros projects.

## Project Overview

This is the **cPanel ELevate** project — a Perl-based tool that performs in-place OS
upgrades for cPanel installations (e.g. CentOS 7 → AlmaLinux 8, Ubuntu 20 → 22, etc.).
It wraps the [Leapp Project](https://leapp.readthedocs.io/en/latest/) for RHEL-based
systems and `do-release-upgrade` for Ubuntu-based systems.

## Language and Runtime

- Written in **Perl**, packed into a single fat-packed script (`elevate-cpanel`).
- Uses cPanel's bundled Perl at `/usr/local/cpanel/3rdparty/perl/536/bin/perl`.
- Library modules live under `lib/Elevate/`.
- The entry point is `script/elevate-cpanel.PL`, which is packed via `maint/perlpkg.static`.

## Building and Testing

- **Build**: `make build` — produces the fat-packed `elevate-cpanel` script.
- **Test**: `make test` — runs `sanity` (syntax check all `.pm` files) then the test suite
  via `yath` (with 8 parallel jobs).
- **Full**: `make` — runs build, test, and coverage.
- Tests live in `t/` and use standard Perl testing conventions (`Test::More`, etc.).
- Always run `make test` after making code changes to verify nothing is broken.

## Repository Structure

- `lib/Elevate/` — Perl modules (components, blockers, OS detection, stages, etc.)
- `script/elevate-cpanel.PL` — main script source
- `t/` — test files
- `maint/` — build tooling
- `.github/workflows/` — CI workflows (OpenStack integration tests per OS target)
- `docs-website-src/` — Hugo-based public documentation website source
- `docs/` — built website output (do not edit manually; generated by CI)

## Public Documentation Website

The public docs site at <https://cpanel.github.io/elevate> is built with
[Hugo](https://gohugo.io/) from source in `docs-website-src/`.

- Content lives in `docs-website-src/content/` as Markdown files.
- The site is built and deployed automatically via the `.github/workflows/website.yml`
  CD workflow on every push to `main`. Hugo compiles the site into `docs/`, which is
  then force-pushed to the `docs` branch by the workflow.
- **Never manually edit files in `docs/`** — they are regenerated on every deploy.
- To update documentation, edit the Markdown files under `docs-website-src/content/`.
- To preview locally: run `hugo -D` from the `docs-website-src/` directory
  (requires Hugo v0.91.2).

## Commit Message Format

Commits follow the cPanel/WHM convention:

1. **Subject line**: Short summary (imperative mood, ≤50 chars), no case number.
2. **Blank line**
3. **Body**: Detailed description; **must begin** with `Case PROJECT-XXXXX:` if a ticket/case exists (use the branch name as the case number when on a case branch).
4. **Trailers** (in this order):
   - `Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>`
   - `Changelog:` — leave empty for internal-only changes; describe user-visible changes otherwise.

`Changelog:` **must always be the last line** of the commit message.

## Conventions

- The sections above are the team's rules: build and test with `make`, commit in the cPanel
  format, edit the public site only under `docs-website-src/content/`.
- `elevate-cpanel` is generated by `make build` from `script/elevate-cpanel.PL` and `lib/`; never
  edit it by hand (`.claude/settings.json` denies it).
- `docs/architecture.md` is the one hand-written page in `docs/` (the human architecture doc); the
  Hugo build writes everything else there, and the published site carries it too.
- `make release` pushes `main` to the public `cpanel/elevate`: everything committed here ships
  publicly, so never commit a secret, an internal hostname or a customer detail.
- Pull requests go through `/usr/local/cpanel/build-tools/merge_request --agent --to=main
  --description "$(cat body.md)"`; the `unit-tests` and `cplint` checks are required on `main`
  (the org's `EndGame branch-main` ruleset).
- Harness files live under `.github/` (CI scripts in `.github/workflows/scripts/`), never at the
  root. The commit gate needs `git config core.hooksPath .githooks` once per clone; a Claude Code
  session sets it on start (`.claude/hooks/enable-githooks.sh`), so only a clone no session opens
  needs it by hand.

## Constraints

- **Boundaries** (the Damage Control hub's contract, `cpanel-whm-dc-hub`
  `system/architecture/contract.yaml`). ELevate runs as root and upgrades the OS under a live
  cPanel & WHM server, so it must not open a path the product closes:
  - BOUND-001 — user-context code reaches root only through an audited admin bin; ELevate never
    installs a setuid helper or a root-run hook a cPanel user can reach, and its systemd unit runs
    only the script in `/usr/local/cpanel/scripts/`.
  - BOUND-002 — a root process drops privileges before it touches user files; ELevate works on
    system paths (`/etc`, `/var/cpanel`, `/usr/local/cpanel`, the package database) and never
    follows a path a user controls as root.
- **Never leave a server half-upgraded without a way on.** A new component implements `check`,
  `pre_distro_upgrade` and `post_distro_upgrade` (`lib/Elevate/Components/Base.pm`) and joins
  `@CHECKS` in `lib/Elevate/Components.pm` (the order matters); a stage that fails must leave
  `--continue` able to resume it.
- **Tests never touch the live system** — no real package manager, reboot or network in `t/`; mock
  with `Test::MockFile` and `Test::MockModule`.
- **Never bypass the commit gate** (`git commit --no-verify`); the engineering-harness plugin's guard
  denies it, and `.githooks/commit-msg` reports the cPanel format.
- **Never run `make release` or `make bump_version`** without the maintainer asking: both push
  to the public and internal remotes and move the `release` tag every server updates from.

## Domain context

ELevate is the supported path from an end-of-life distribution to its successor for a server
already running cPanel & WHM: `/scripts/elevate-cpanel --check` reports blockers, and `--start`
drives five stages across reboots through the `elevate-cpanel.service` unit
(`docs/architecture.md`). cPanel & WHM downloads it from the `release` tag of `cpanel/elevate`
(`Cpanel::Elevate`). The repository belongs to the Damage Control pod, in the `build-platform`
scope of the `cpanel-whm-dc-hub` knowledge hub.

## Tools

- **Perl toolchain** — cPanel's Perl 5.36 under `/usr/local/cpanel/3rdparty/perl/536/bin/`
  (`perl`, `prove`, `yath`, `perltidy`); `t/critic.t` runs Perl::Critic over `script/` and `lib/`.
- **cplint** — runs on every pull request (the `cplint` job) and through `merge_request`.
- **Pull requests** — `/usr/local/cpanel/build-tools/merge_request --agent --to=main
  --description …` (runs cplint, pushes, opens the pull request, links the Jira case).
- **MCP servers** — none wired (`.mcp.json` declares an empty set); do not call one.
